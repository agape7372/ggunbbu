## 2. 단위 계약 (이게 없으면 델타는 무의미하다)

- **fps = 60** [정본, 단 조건부] — `FUN_0040bf50` 프레임 페이싱(`timeGetTime` 16ms 게이트 +

## 5. 점프·밑면 접촉 판정 — DEVLOG:518 A/B 해소 ★확정 (2026-08-30 3차)

**결론: "관통이냐 정지냐"는 이분법 자체가 틀린 질문이다. 원작은 플레이어 포즈에 따라 5갈래로 갈린다.**
평범한 점프는 **막히고**(관통 아님), 공중공격은 **뚫으며 부순다**. → DEVLOG:518은 **B 쪽**이 맞고,
**ROADMAP 08-30 "밑면 접촉 정정"이 옳았다.**

### 범인 함수 `FUN_00405140` (플레이어×층 충돌 페어 처리기)
플레이어 자신의 상태 함수가 아니라 **별도의 충돌 페어 노드**의 처리기다
(`+0x20`=플레이어 포인터, `+0x24`=층 포인터, 층의 `+0x0c`=부모 건물).

- 층 밑면선 `L = floor[+0x24] + 0x1b8 + building[+0x20]`
- 수평 AABB: `floor.x < player.x+0x58 && player.x+0x28 < floor.x+0x50`
- **`switch (player[+0x50])`** — 포즈 ID로 분기:

| `+0x50` | 포즈 | 밑면 접촉 시 |
|---|---|---|
| 1 | 지상 공격 | `y+10 < L` → **층 파괴**(점수·파편·화면흔들림) |
| **3, 0xe** | **평범한 점프/공중** | `y+0x30 < L` → **정지**. `y_acc = L−0x2f`, `vy = building[+0x24]/128 + 1.0` |
| 4 | 공중 공격 | **6프레임 선행 스윕**(`vy×6.0 + y < L`) 또는 `y+10 < L` → **층 파괴** |
| 6 | 공중 필살 | `y+0x30 < L` → 정지. `y_acc = L−0x30`, `vy = building[+0x24]/128` (**+1.0 없음**) |
| 그 외 | — | **아무 일 없음 = 관통** |

상수: `DAT_0041c244 = 0.0078125 = 1/128`, `DAT_0041c224 = 1.0`, `DAT_0041c240 = 6.0`(스윕 프레임).
### 세 충돌 처리기의 담당 ★확정 (2026-08-30, 스폰 체인 역추적)

세 주소는 **immediate 상수로 어디에도 등장하지 않는다** — 각 함수 직전 75바이트 **스텁**이
노드를 조립해 오브젝트리스트 삽입 공용 함수 `FUN_004128c0` 에 넘긴다. 스텁의 직접 호출자는
정확히 1곳씩이고(E8 call), 그 호출자가 곧 **장애물 스폰 시점**이다.

| 처리기 | 스텁 | 스폰 체인 | 담당 | 확신도 |
|---|---|---|---|---|
| `FUN_00405140` | `FUN_004050f0` | ← `FUN_00407990` ← `FUN_0040a5f0` | **낙하 건물 변형A의 층** | 확정 |
| `FUN_00407690` | `FUN_00407640` | ← `FUN_0040acb0` ← `FUN_00409760` | **낙하 건물 변형B의 층** | 확정 |
| `FUN_00405490` | `FUN_00405440` | ← `FUN_00407e30` ← 타이머 스포너 `FUN_00407db0` ← `FUN_00407d40`×3(레인) ← 3레인 컨트롤러 `FUN_00407c50` | **주기적 소형 낙하물** | 유력 |

- 변형A/B는 같은 스프라이트(ID `0x2d`, 640×480 블릿)를 쓰고 상태전이를 공유한다(둘 다
  `FUN_00409e70` 으로 복귀) — 별개 오브젝트가 아니라 **같은 건물-드롭 사이클의 두 파도**다.
- **A와 B의 차이는 파라미터뿐**(포즈 5-way 스위치는 완전 동일): 밑면선 오프셋 `0x1b8` vs `0x1c2`
  (10px), 정지 vy의 `+1.0` 보정 **유무**, 히트플래그 필드 `+0x30/+0x34` vs `+0x3c/+0x40`.
  통합하지 않고 복붙한 당시 관행으로 보인다.
- **⚠ 변형B의 스폰 x = `100/190/280/370/460` (90px 격자) — 플레이어 3레인 격자(136/256/376, 120px)와
  맞지 않는다.** 변형A의 스폰 x = `140/260/380` 은 3레인과 정렬된다. 따라서 B를 "5레인"이라
  부르면 안 된다. **왜 5곳·90px인지는 미확정** (다른 폭의 낙하물일 가능성).
- `FUN_00405490` 만 **11케이스 상태기계**다(수평이동 `+= -0x200/lane`, 포즈10=공중가드에서
  `vy = 8.0` 아래로 튕김, 연쇄 타격판정 `FUN_004129b0/f0`). 건물 층과는 **물리 계약 자체가 다르다**
  — 코드 중복이 아니라 필연적 분리다. 실제 렌더는 스프라이트 `0x2c` 를 160×120 으로 블릿(건물의 1/16).
  종류명은 크기·주기성·바운스 정황상 "좁은 낙하물(버터바류)"이 유력하나 **스프라이트 실측 미수행**.

### 실측이 코드와 정수 단위로 일치한다 [정본]
| 관측 | 모델 |
|---|---|
| 스냅 후 `y=277` | `y_acc = L−47` → **밑면선 L = 324** |

| 리셋된 `vy = 0.359375` | `(0.359375 − 1.0) × 128 = **−82.0 정수**` = `building[+0x24]` ✓ |
| 이후 vy 증분 정확히 **1/128** | 건물 낙하 카운터가 프레임당 +1 ✓ |
| 이후 y 증분 정확히 **+1px** | 같은 카운터가 밑면선을 프레임당 +1 밀어올림 ✓ |

CSV의 vy 고유값 30개를 `(v−1)×128`로 역산하면 전부 정수(−82,−81,−79,…)이거나
`정수 + 12.8k`(중력 0.1을 k번 먹은 프레임, 0.1×128=12.8)다. **자유 파라미터는 밑면선 324 하나.**

### 리메이크가 놓치면 안 될 세부 3가지
1. **포즈 4(공중공격)만 6프레임 선행 스윕**을 쓴다. 빠르게 상승하는 공중공격은 층을 뚫으며 부수지만
   평범한 점프는 걸린다. **이 비대칭이 원작 게임감의 핵심**이다.
2. **정지 후에도 매 프레임 재판정**된다. 접촉이 유지되는 동안 `y_acc`가 매 프레임 `L−0x2f`로 재고정되어
   플레이어 y는 물리가 아니라 **건물의 침하 속도를 따라간다**(관측 +1px/프레임).
   "vy=0으로 만들고 낙하 시작"으로 구현하면 원작과 다르다.
3. 포즈 3은 정지 후 `return` — 포즈 6 블록으로 폴스루하지 않는다.

### 정정 — 초판·2차의 오류 3건
- 초판: *"점프 상태 `FUN_004028f0`에 충돌 분기가 없다 → 관통(A)"*. 분기 부재는 사실이나 결론이 틀렸다.
  충돌은 **플레이어 바깥의 페어 처리기**가 수행하고 플레이어 필드를 직접 쓴다.
- 3차 1보: 범인을 `FUN_00405490`으로, 공식을 `vy = 낙하속도/128`로 적었다. **둘 다 부정확** —
  실제 트리거는 `FUN_00405140`이고 공식에 **`+ 1.0`이 빠져 있었다**(그래서 역산이 정수로 안 떨어졌다).
- 2차: "반경 200px 내 오브젝트 0개"는 필터 오류. 층 객체는 `+0x20`이 x가 아니라 층 인덱스이고,
  **충돌 페어 노드의 `+0x20`/`+0x24`는 좌표가 아니라 포인터**다.

→ 교훈: **부재 증명은 정적 분석으로 하지 마라.** 그리고 역산 결과가 정수로 떨어지지 않으면
반올림해 넘기지 말고 **식이 틀렸다고 의심하라**(45.95를 46으로 읽어 한 번 틀렸다).

## 5-B. ★레인 구조 — config.ts와 정면 충돌하는 발견

## 7. 데이터 포맷 (명세만 — 원작 에셋·덤프는 레포에 넣지 않는다)

- `image/*.bmp` = 8bpp 팔레트. `char.bmp` 128×128 셀 5×5(22칸 사용), `slash.bmp` 18프레임(리치 12→120px 성장), `bil10/20/30.bmp` 480×600.
- `data/*.dat` = **확장자만 바꾼 표준 BMP/MIDI** (암호화·압축 0). 단 `023/024.dat` 2개만 예외.
- **`023/024.dat` = 조건부 XOR 텍스트** [정본, 해독 완료 2026-08-30]. 로더 `FUN_00408f50` @ `0x408f50`.
  알고리즘: 바이트 `< 0x20` 은 **그대로 통과**(그래서 CRLF가 파일에 평문으로 남는다),
  `>= 0x20` 이면 **XOR 0x3A**. 단 XOR 결과가 `0x20` 미만으로 떨어지면 **XOR을 취소하고 원본 유지**.
  디코드 후 인코딩은 **Shift-JIS**. `0xFF` 는 리스트 종료 센티널이라 raw 데이터에 절대 안 나온다
  (원문의 `0xC5`는 `^0x3A = 0xFF` 충돌을 피하려 별도 리매핑).
  ⚠ 단순 XOR 전수조사로는 못 찾는다 — 0xD9가 cp932를 코덱 에러 없이 통과하는 **거짓양성**이 있다.
  호출부: `STATE_40d560`/`STATE_40e2d0` 의 `case 4`(오프닝) · `case 7`(엔딩).
  내용: 023 = 오프닝 내레이션 55줄, 024 = 연표(1986~2004) + 엔딩 + 스태프 크레딧 122줄.
  **한국어 재배포판인데 이 두 파일만 일본어 원문 미현지화 상태**다.
  스토리 요지(달에 토끼가 산다 → 교신 성공 → 토끼가 인간에게 항복 요구)는 아래 9절 6번 참조.
  **원문 텍스트는 레포에 반입하지 않는다** — 포맷·주소·요지까지가 이 문서의 범위다.
- `save/replay*.rep` = 입력 리플레이 20슬롯. 신포맷 `[i32 hdr][i32 N][N×(frame, keycode)]`, 구포맷(11번 이후)은 keycode 상위 바이트에 카운터 동반. 전 파일 `8+N*8 == size` 검증 통과.
- `save/score.sav`·`daini_score.sav` = 10×(int,int). 저자 최고기록 1막 17,048,529 / 2막 32,149,395.
- ⚠ **exe 실행 시 리플레이 링버퍼가 밀린다**(DeleteFileA+MoveFileA 임포트). 원본 폴더는 백업 후 사본에서만 실행할 것.
